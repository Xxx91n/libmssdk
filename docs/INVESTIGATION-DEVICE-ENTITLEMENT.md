# 调查：设备身份与整曲权益的关系（[#10](https://github.com/sodahub-org/libmssdk/issues/10)）

> 要回答的问题只有一个：**用服务自己生成的设备号去请求上游取流，为什么只拿到试听片段？**
>
> 结论先行：**设备号不是原因。** 同一份 Cookie、同一首曲子，把设备号换成毫秒时间戳、
> 全新的随机 16 位、服务落盘的那一份，甚至**完全不发 Cookie**，结果一模一样。
> 决定整曲还是试听的是**曲目本身对该账号的授权等级**：有的曲目在任何一种设备号下都给出
> 整曲 + 6 档（含 lossless），有的在任何一种设备号下都只给 30–60 秒单档试听。
> 当初扫的那 7 首属于后者。

---

## 一、三种解释各自要怎么被检验

调查开始前立了三种解释（也是这张票的原始表述），公开记录里同类症状绝大多数归因于前两种。
每一种都配一条**只有它成立时才会出现**的读数：

| 解释 | 如果成立，会看到 | 如果不成立，会看到 |
| --- | --- | --- |
| Cookie 不完整 | 带 Cookie 与不带 Cookie 结果不同；或某个登录态接口读不到用户 | 两者结果相同，且整曲照常出现 |
| 签名构造有误 | 回包是 `HTTP 200 + 0 字节`，或改了 headers 就空 | 回包是结构完整的 JSON（非空即代表服务端认了这个签名） |
| 签名设备 = 登录设备 | 只有「与账号登录设备一致」的设备号能拿整曲，随机设备号一律试听 | 随机设备号也能拿整曲 |

第三条最戏剧性，也最容易抢跑，所以它被单独安排了一对多组对照：
`good-ts`（每次请求换一个毫秒时间戳）与 `rand16`（每次运行换一个全新的随机 16 位设备号）——
这两个值在数学上都不可能是任何真实登录设备，如果它们能拿到整曲，绑定说就直接被证伪。

`sig-mismatch` 是签名有效性对照：故意让 URL 里的设备号与签名器 `init()` 用的设备号不一致。
`no-sign` 是必要性对照：同样的请求不发签名。它决定上面所有读数能不能被解释成「签名被接受」——
没有它，「非空回包」这句话没有含义。

## 二、复现步骤

前置条件：

1. 本机 `vendor/soda-music/` 里有**你自己**客户端里的 `bdms.node` 与 `metasecml.dll`（不入库）。
2. 本机有一份你自己的登录 Cookie。默认从 `%APPDATA%/sodam/config.json` 的 `cookie` 字段读；
   也可以 `export LIBMSSDK_COOKIE='…'`（进程环境变量，不落盘）。
3. 两首曲目号：一首你在播放器里**确实听到过整曲**，一首**只听到过试听**。
   不知道哪首算哪首时，先跑 `--arm seo-web`（免签名）看 `streamDurationSeconds`：
   落在 30 / 60 附近的就是试听级候选。该接口的 `track.duration` 是 0，
   所以它只能佐证试听长度，不能用 `fullTrack` 判整曲。

```bash
# 只打印矩阵，不打网络
node tools/entitlement-matrix.mjs --list

# 正对照：应当是整曲。这一条不过，后面所有读数都没有意义
node tools/entitlement-matrix.mjs --track <拿到过整曲的曲目> --arm good-ts

# 一次跑完（8 条签名请求 × 2 轮 + 1 条免签名）
node tools/entitlement-matrix.mjs --track <拿到过整曲的曲目> --repeat 2

# 关键的一条：把曲目换成「只有试听」的那首，其余一切不动
node tools/entitlement-matrix.mjs --track <只有试听的曲目> --arm good-ts
node tools/entitlement-matrix.mjs --track <只有试听的曲目> --arm service-id
node tools/entitlement-matrix.mjs --track <只有试听的曲目> --arm no-cookie

# 必要性对照：不发签名
node tools/entitlement-matrix.mjs --track <拿到过整曲的曲目> --arm no-sign
```

请求预算：整份矩阵跑两轮约 16 次上游调用，加跨曲目验证本次共约 26 次签名请求。
每条 arm 与 `good-ts` 基线之间**只允许动它声明出来的那几个字段**，这条不变量由
`test/entitlement-matrix.test.mjs` 离线守住（改一个字段就测不出来是谁在决定权益）。

### 判据

| 读数组合 | 判定 |
| --- | --- |
| `good-ts` 试听 | 实验本身不成立（复刻不了已知会成功的那条请求），先查形状，不要往设备号上想 |
| 同一首整曲曲目下，`rand16` / `service-id` / `no-cookie` 都是整曲 | 设备号与 Cookie 都不是变量 |
| `no-sign` 是 `200 + 0 字节` | 上面那些「非空回包」确实等于签名被接受 |
| 曲目 A 在所有 arm 下整曲、曲目 B 在所有 arm 下试听 | 决定因素在曲目层，不在凭据层 |
| 只有匹配登录设备才给整曲、随机设备号给试听 | 设备绑定成立（**本次没出现**） |

## 三、本次读数

环境：Windows 原生 Node + 本机 `vendor/soda-music/bdms.node`；同一份 Cookie；2026-10-28。
签名只记长度（`X-Helios` 48，`X-Medusa` 828–840），设备号只留首尾。

### 同一首「已知能拿到整曲」的曲目，换着花样动凭据

| arm | 改动 | 结果 |
| --- | --- | --- |
| `good-ts` | 基线：设备号=毫秒时间戳（每次不同） | **整曲** 6 档，含 lossless/flac |
| `rand16` | 只换成两个全新的随机 16 位设备号（两轮） | **整曲** 6 档 |
| `service-id` | 只换成本服务落盘的那一份固定 16 位 | **整曲** 6 档 |
| `probe-shape` | 现状 `probe` 的完整形状（3.8.0 + `local-user: 0` + 服务身份） | **整曲** 6 档 |
| `app380` | 只把版本号与 UA 推到 3.8.0 | **整曲** 6 档 |
| `localuser0` | 只把 `x-luna-is-local-user` 从 1 改成 0 | **整曲** 6 档 |
| `no-cookie` | 只不发 Cookie | **整曲** 6 档 |
| `sig-mismatch` | URL 用时间戳设备号，签名器 `init()` 用另一个随机 16 位 | **整曲** 6 档 |
| `no-sign` | 同样的请求，不发 `x-helios` / `x-medusa` | `HTTP 200 + 0 字节` |

`rand16` 两轮的设备号与 `service-id`、`good-ts` 全都不同，结果一致。
`probe-shape` 就是当初扫 7 首全试听时用的那一份形状，今天在同一首整曲曲目上是整曲。

### 换曲目，其余一切不动

| 曲目 | 曲长 | `good-ts`（时间戳） | `service-id`（固定 16 位） |
| --- | --- | --- | --- |
| 整曲样曲目 1 | 185.3 s | 整曲 6 档（lossless 1572 kbps） | 整曲 6 档 |
| 整曲样曲目 2 | 109.0 s | 整曲 6 档 | 整曲 6 档 |
| 试听样曲目 1 | 278.5 s | 60 s 试听，仅 `higher` 1 档 | 60 s 试听，仅 `higher` 1 档 |
| 试听样曲目 2 | 292.7 s | 30 s 试听，仅 `higher` 1 档 | 30 s 试听，仅 `higher` 1 档 |

试听样曲目 1 正是当初 Wine 原型里逐首扫到的那一首（60 s / 278.5 s），
两种设备号形状读数相同；免签名的 `seo-web` 对同一首回包里 `video_duration` 也是 60.001，
也就是免签名接口早把它当试听级发出来了。
（`seo-web` 的回包结构不同，本票不拿它判整曲，只用它佐证「试听长度」这个观察。）

### 一条容易误用的字段

`track.label_info.only_vip_download` 在**整曲曲目和试听曲目上都为 `true`**，
不能拿它判断「这首曲子这个账号能不能听整曲」。能判定的只有
`video_model.video_duration` 与 `track.duration` 的关系（也就是 `probe` 现在用的
`fullTrack` 判据）。

> 上表四首曲目的曲目号只留在本机，不入库——它们能反出个人收听记录。
> 结论不依赖具体曲目号：换成你自己的「一首已知整曲 + 一首已知试听」照第二节跑一遍即可。

## 四、结论

1. **「签名设备必须与账号登录设备一致」不成立。** 每次请求都不一样的毫秒时间戳、
   每轮都不同的随机 16 位设备号、服务落盘的固定设备号，三种都拿到同样的整曲。
   这三个值不可能是任何一台真实登录设备。
2. **「Cookie 不完整」不成立。** 同一首曲目的整曲结果在带 Cookie 与完全不带 Cookie 时相同。
   也就是说，在这条接口上，**应用签名本身就是取流凭据**，账号 Cookie 不是决定整曲与否的变量。
3. **「签名构造有误」不成立。** 所有带签名的 arm 都拿到结构完整的回包；
   唯独 `no-sign` 拿到 `HTTP 200 + 0 字节`。这既说明签名确实被校验，也说明
   「非空回包 = 签名被接受」这个推理在本接口上成立。
4. **真正的原因是曲目层面的授权差异。** 同一份凭据、同一个签名器、同一台机器下，
   有些曲目给出整曲全部档位，有些只给 30–60 秒单档试听，且这个结果与设备号无关、可重复。
   当初扫的 7 首全部落在后者——那不是设备号的锅，是选样就把试听级曲目挑出来了。

一张票只负责分清责任：**这件事不在本仓库，也不在客户端的设备号上。** 上游对「哪首曲子能给整曲」
的判定本票不再往下追（会员层级 / 地区授权 / 单曲购买，具体是哪一种需要另一份带已知权益账号的对照）。

### 顺带被削弱的一条既有说法

`sig-mismatch`（URL 设备号与签名器设备号不一致）没有被拒。但**不能就此证明上游不校验设备一致性**：
那首曲目在不带 Cookie、不带任何一致性时本来就是整曲，这条对照没有区分力。
要真正证伪「成套」要求，需要一首「只有成套才给整曲」的曲目，本次没有找到。
本仓库继续按「签名器与 URL 用同一份设备号」实现是自洽且更省事的（避免每请求重新 `init()`），
只是**不该再把它当成上游的强制要求来写文档**。

## 五、多人共享同一份设备身份的后果

- **权益角度：没有后果。** 既然整曲与否与设备号无关，共享一份身份既不会让谁的权益变差，
  也不会让任何人凭共享身份多拿到什么。反过来说，**设备身份不是访问控制**，
  不要指望用「每人一个设备号」来限制谁能拿到整曲。
- **上游视角下的风险：风险变大了，且集中在签名器这一台机器上。**
  签名即凭据、且账号 Cookie 不是必要变量，意味着「一个签名器 + 一个出口 IP + 一个设备号」
  可以为任意多人取任意有授权的整曲。上游看到的画像是「同一个设备号高频请求大量不同曲目」——
  这是最典型的爬虫特征，被风控时受影响的是这台签名器与它的 IP，而不是某个用户。
  这正是本仓库总纲里「删掉会替别人打上游的诊断接口、按 IP 分桶限流」那两个决定的理由所在。
- **可接受的共享形态**：一个签名器只服务一小撮可预期的人（家庭/小团队），
  并把速率限制在自己的容量与画像可解释的范围内。公开池化一台签名器，等于把自己的 IP
  押上去替所有人承担风控。

## 六、确实指向客户端的那件事（与本票结论无关，但是独立缺陷）

调查过程中在代码层面确认了一件事，它**不是**试听问题的原因（第四节 1 已经排除），
但值得在客户端仓库单独修：

- `libresoda` 的 `device_id` / `iid` / `fp` 配置项默认为空，空值会落到
  `Date.now()` 与 `Date.now()+1`（见 `src/soda/mod.rs` 的 `pc_app_params_with`），
  于是**每个请求的设备号都不一样**；`sodam` 的设置界面根本没有这三个字段可填，
  所以普通用户永远走的是这条回退路径。
- 后果有两层：一是上游会看到「同一台机器、同一 Cookie、设备号每请求一变」的画像；
  二是签名器每次都要重新 `init()`（本仓库 `src/bdms.mjs` 按设备号变化重新初始化），
  而 `init()` 之后的第一批签名落在短签名窗口里——本次读数里 `X-Medusa` 多数是 828 而不是 840，
  就是这个窗口。**本次所有读数都被上游接受了**，但这只是 `track_v2` 一条接口，不能外推。
- 要改的是那两个仓库：`sodam` 的暴露一个持久化的设备身份字段（或在首次运行时生成并存进
  `config.json`），`libresoda` 的空值回退不该产生「每请求新值」，而应产生「每进程新值」
  或直接拒绝并提示配置。本票不代替那两个仓库做这个决定。

## 七、未决项

- 曲目层的授权具体由什么决定（会员层级 / 地区 / 单曲购买）——需要一个已知权益的账号做对照。
- 「只有成套才给整曲」的曲目是否存在，即上游到底校不校验设备一致性——见第四节末。
- 其它接口（不止 `track_v2`）上签名有效性是否同样宽松。
- `probe` 的试听提示文案按本结论改掉了「设备指纹不匹配」这一归因；
  若日后发现能判定的字段，应把提示改成可行动的那一句。

## 八、敏感边界

- Cookie 只在本机进程内使用，不写盘、不打日志、不进任何输出文件；输出里只出现「几个字段」。
- 签名值只记长度；设备号只留首尾三位。
- 本文的曲目号与读数只说明响应形状，不含任何凭据。
- 把这份结论贴到 issue / PR 时，同样不要带 Cookie、签名值、完整设备号或本机路径。
